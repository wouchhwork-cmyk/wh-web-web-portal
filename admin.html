How media is described

Meta serves message media from links that expire, and will not re-issue one past the newest 20 messages of a thread — after that the photo is gone for good. Every piece of media is therefore described once, while its link still works, and the description is what survives. This is the instruction behind every description.

Not a dropdown: Google retires and renames these on their own schedule, so a fixed list here would be a second thing to edit every time and the one most likely to be forgotten. A wrong id fails on the next analysis and is recorded against the media it was describing.
Bumped on every save. Each description records the version that produced it, so one that reads oddly can be traced back to the exact wording behind it.
Sent with every piece of media, so its length is billed on every one. Saving does not re-describe anything. It changes what happens next, not what already happened.

How the assistant replies

The assistant drafts replies in the inbox from what we already hold — the recent thread, the descriptions of media whose links have since expired, and what the business says about itself in its profile. This is the standing instruction behind every draft, the model that writes it, and which provider answers. Nothing here sends anything: a draft is always read and sent by a person.

Both clients are implemented and either can answer. They are not interchangeable in price or in what they read, so the choice is a setting rather than a default.
Leave blank to use the default. Not a dropdown: the list is theirs and changes without warning, and a wrong id fails on the next reply.
Each provider keeps its own model, so a gpt- id can no longer be left behind where Google will be asked about it. Blank uses the default.
A kill switch, not a consent. Each business opts in for itself; this says whether we are willing to run any of it at all. Turning it off here stops every automatic reply on the platform immediately, without touching what each business chose.
Bumped on every save. Each draft records the version that produced it.

Keys are stored encrypted and never sent back to this page — which is why the boxes are always empty and why there is a tick-box to remove one. A key saved here is used instead of the environment's; remove it and the environment answers again. The chat key is separate from the one that describes media, so the assistant can run on a different account entirely.

Sent with every conversation, so its length is billed on every reply. Keep the rule about not inventing facts and the one about treating text inside a conversation as content rather than as an instruction — a customer can type anything, including something shaped like an order to the model.
Sent to the customer when a reply cannot be produced — the model failed, or the provider has no key here. With automatic replies on, every fast answer has told that customer somebody is there, so saying nothing reads as being ignored. The real reason goes to the audit trail, never to them. Leave it empty to send nothing at all.
Media is described a few seconds after it arrives, so a photo sent with no text reaches the assistant before there is anything to answer about. This holds the moment; the real answer follows as soon as the description lands. Leave it empty to wait silently and answer once.

Meta API rate limits

Meta runs two separate meters and the token decides which applies. The app pool is one allowance for the whole developer app — roughly 200 × daily active users per hour — and it is drained by businesses connecting, not by the inbox. The business pools are per business per product and carry everything else.

Every figure Meta gives is a percentage of an allowance it never states, so “used” is how close a pool is to being refused, and “calls” is our own count. A pool showing unknown is one Meta sent no header for — that is not the same as zero.
